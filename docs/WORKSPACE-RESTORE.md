# Safe editable workspace restore: contract and staged implementation

Implemented in an isolated worktree on 2026-10-12 from source baseline `beb7fcf663cb45b935b1aab53d60a89e356be9b9`; the final independent parent aggregate passed on 2026-10-12: 4775 total, 4773 passed, 0 failed, 2 skipped (1215750.130935ms, exit0). Release review remains the parent’s final gate. Gate A passed parent review, including fixed-schema preservation and the locked Electron44.7.0 main→utilityProcess SQLite gate. Gate B actual HTTP/CLI/official MCP, local execution fences and renderer checks passed. Gate C passed on the initial Linux production package: ordinary export, restored import/edit/undo/preview/export, three normal native exits, full application recreation, exact captured-row/history/source/backup preservation and real output probe/decode/audio checks. The initial unclassified ordinary Mock schema refusal was preserved and corrected with an exact optional profile, followed by fresh focused/Electron/build/native verification. No live provider calls are part of this slice; Mac/Windows native acceptance remains unperformed.

## 1. Smallest useful release

Restore a verified backup into a **new private working directory**, then let the user open it, import local media, edit saved projects/canvas/shot/reference/subject/timeline metadata, undo/redo, preview and export new local video. It is an independent branch at the backup's capture time; later changes in the original workspace are not merged.

All captured task/approval/intent identities stay historical and held, irrespective of original status. A restored queued, running, unknown, approved or terminal record cannot execute, reconcile remotely, publish a staged result, change outcome or become the parent of a retry. Status/claim/request/receipt fields are not renamed, cancelled, acknowledged or rewritten to implement that hold.

The restored-v1 profile additionally declines **new** video/image generation, Agent runs and approvals, Comfy requests/observations, frame extraction and waveform decoding. Existing finished media, versions and already-ready peaks remain readable under their existing ownership rules. Ordinary, non-restored workspaces retain all current behavior. This is an explicit temporary limitation of the restored branch, not a global feature removal.

A directory copy without safe editing and actual export is not a shipping milestone.

## 2. Offline interface and publication

Local entry: `node apps/cli/src/backup.mjs restore --directory <verified-backup> --destination <new-workspace>` and the shared `restoreWorkspaceBackup` function. The operation is local only; no HTTP/MCP endpoint accepts destination paths or performs restore.

- Accept only backup format 1 and an explicitly supported, fully classified source schema 24. Do not infer compatibility from a maximum version number. Unknown schema objects, inconsistent relational identities or inability to enumerate execution identities refuse activation.
- Verify the original manifest/COMPLETE and every included file before using them, then rehash the copied result. Original backup/source bytes and modes are unchanged. No copied settings, credentials, token, browser state or lock.
- Destination must not exist, overlap the supplied backup, alias a protected path, contain symlinks/reparse-like entries, or bypass current private-storage policy. Fixed `workbench.sqlite`/`server.lock` markers on destination ancestors reject nesting in an existing or active Mioon workspace without reading arbitrary directory contents. Choose a separate independent destination outside the original workspace; format1 does not retain the source pathname, so renamed or uninitialized sources cannot be reliably identified. This is not absolute original-source path detection. New app-owned directories/files use the current private creation modes; existing permissions are never repaired.
- Acquire the destination's compatible exclusive lease. Copy the database to a non-runtime basename. Never publish raw source bytes as `workbench.sqlite` before installing the durable gate and quarantine.
- Build and validate the restored schema in the private candidate. Keep source SQL unopened; only candidate/disposable copies receive SQL. Use trusted-schema-off validation, fixed schema/SQL, no extension/UDF authorization mechanism.
- Install the restoration identity, historical holds, narrow index change, history archive and old-runtime gate in one transaction. Seal/checkpoint/close so the gate is in the main DB, verify absence of uncheckpointed sidecars, fsync files/directories, then publish the launchable filename with no-replace semantics.
- A crash leaves either an unpublished/non-launchable candidate or a fully guarded restored DB. If another process creates the final pathname, refuse rather than replace it. Do not remove an uncertain lock or reuse an incomplete destination automatically.
- A caught publication uncertainty returns generated provenance with an explicit unknown result. A process crash or lost stdout can lose that reply entirely. `restore-status` supports either all exact returned identity fields or the explicit original backup directory plus target: the latter revalidates the complete original backup and fixed target schema/source binding before revealing the current identity. Both return only `observed_guarded` with `durability:not_reconfirmed`; neither proves the earlier command succeeded or its failed fsync was durable. They never publish, repair, resume or rerun. Locked, two-link, partial or mismatched targets remain unchanged and unavailable.
- No automatic desktop data-directory switch. Existing Web `MIOON_DATA_DIR` and Desktop `MIOON_DESKTOP_USER_DATA` can select an explicit new root. For Desktop, restore destination is the new root's `workspace` child. The old root remains available and must not share the restored root's token/session context.

### Fixed offline resource limits

Reuse backup's 512 MiB source-DB, 8 GiB/file, 64 GiB payload, 20,000 files, 8 MiB manifest, 1 MiB stream-chunk and 100 displayed-issue limits. Fixed metadata enumeration is bounded before JS materialization. Additional activation limits: at most 20,000 captured execution/history records and 64 MiB raw captured timeline-history archive; the final candidate DB must still fit 512 MiB. Refuse before publication if those bounds cannot hold. These are app limits, not filesystem free-space guarantees.

Budget temporary DB/candidate/verification copies and SQLite sidecars explicitly in the implementation's disk estimate. Cancellation fences every step and retains ownership until issued I/O settles; no hard real-time kernel-I/O cancellation promise. Captured rows continue counting toward existing lifetime ledger quotas. Held work is excluded only from current active/busy admission. A full lifetime edit ledger remains a visible limit, never an excuse to evict replay identities.

`inventory.complete=false` is not an automatic rejection: known unresolved work and retained partial results are exactly what quarantine handles. Classify every warning. Valid missing-media records can open with visible missing-source warnings and existing export preflight findings plus the normal guarded export failure. Invalid/unbounded task identities or unknown schema cannot be treated as zero held work. No silent loss of copied stage files or receipts.

## 3. Durable schema and preservation

A normal server creates an optional, fixed Mock provider ledger even when no generation is submitted. Restore classifies its complete two-table/three-index structure separately from the base schema; partial, altered or unknown provider SQL remains unsupported. The original provider ledger rows, raw snapshot strings, counters and submission sequence stay historical. The restored server does not construct that provider. Both profiles passed the fixed-source Node preservation/legacy gate and the locked Electron main→utilityProcess gate. The Mock profile additionally keeps immutable provider-ledger digests and the exact submission sequence, with bounded prehash validation; it does not grant provider execution authority.

Reserve schema 25 for this first restored profile, with explicit profile classification rather than a permissive numeric fallback. Non-restored schema24 startup remains on its existing path. Future migrations must deliberately support both profiles; schema25 is not a claim that any DB with that marker is safe.

Minimum additions:

1. Immutable singleton restoration metadata: restoration ID/current workspace-origin UUID, source backup ID/manifest hash/raw DB hash, source schema, profile and creation time. Origin is stable across backend restarts.
2. Fixed-kind captured identity/held-key metadata for all captured jobs/exports, image reviews/tasks/remote runs/observations, frame tasks, Agent runs/steps/proposals, durable edits and disposable pending derivations. Held keys bind their actual existing namespace, operation and exact original intent. No workspace-global dedupe reinterpretation.
3. `edit_tasks.executionEpoch`, defaulting to a fixed captured value, never the current origin. Additive column, immutable after insert. Replace only its pending-lane unique index with `(projectId,lane,executionEpoch)` under the existing predicate. Preserve `UNIQUE(lane,requestId)`, sequence high-water mark, all old columns, raw input and state transitions. A new insert that omits valid current origin fails closed.
4. One fixed new-export origin relation, atomically inserted with each new export row and its existing receipt. It binds export ID/project/origin, exact existing request namespace/key/hash and a digest of the immutable export identity/frozen snapshot. Storyboard request hash alone does not cover its frozen snapshot. No retroactive binding of captured exports. Unbound is held, not assumed new.
5. An immutable archive of captured `timeline_history` rows and capture cursors, copying exact original SQL column values/raw snapshot strings. Normal `recordEdit` deletes the redo tail on branching (`timeline.mjs:113`); that behavior may continue in live history, but the captured evidence remains accessible in the archive. Do not claim live editable tables remain byte-identical after legitimate new edits.

All original row IDs, SQL types/nulls, input/receipt/snapshot TEXT/BLOB bytes, sequence positions and immutable evidence must compare exactly immediately before/after construction. After user edits, mutable live project/timeline fields may change as usual; captured task/approval/receipt records and archived history may not. Original backup SQLite stays byte-for-byte intact. Added schema necessarily changes the restored SQLite file hash.

Add fixed update/delete/replacement protections where captured execution records currently lack them. Test `INSERT OR REPLACE`, recursive-triggers modes and rollback explicitly; a delete trigger alone is insufficient. No generic raw table executor or client-writable authority flag.

## 4. Older binary fail-closed gate

Current `packages/business/src/db.mjs:64` unconditionally runs `INSERT OR IGNORE INTO schema_version VALUES(1)` before store return. The audited predecessor `1536878` has the same mandatory insertion, and earlier repository bootstrap history provides a second dangerous-startup fixture.

Install a permanent main-schema `BEFORE INSERT ON schema_version` trigger that raises a fixed error for legacy markers 1–24, plus immutable marker protections. The guard must not depend on a sidecar, restore-state row still existing, max-version comparison, environment flag, or registered function. Patched `openStore` validates the complete fixed SQL structure and source binding of schema25 **before** running legacy bootstrap, skips that bootstrap only for the valid profile, then shares the existing store-method construction. Partial/malformed restore artifacts refuse without a v24 fallback. Startup or migrations must never drop, disable or temporarily replace the barrier. Schema24 input receives the same fixed-object classification before any imported trigger can execute.

Required proof: execute SHA-pinned baseline `beb7fcf` and historical bootstrap/server/migration entrypoint sources against restored fixtures, with downstream dependency probes that detect forbidden construction. This is frozen-entrypoint evidence, not execution of complete historical packaged binaries; no store return, provider construction, service recovery, listener, worker, POST/GET/download, captured-work decoding/rendering/extraction or publication. Record Desktop tool-validation subprocesses separately: its existing pre-backend `-version`/`-encoders` checks are not captured-work processing. Also copy only the closed SQLite file to a new root and repeat. Old migrate-data copies the DB and therefore retains the barrier. Patched migrate-data refuses complete and partial restored evidence before creating its target. It inspects a private streamed copy and migrates those exact checked bytes, rechecking the source inode/content metadata and cold lock/WAL/journal state around asynchronous work. The legacy ordinary migration keeps its prior size acceptance: a1MiB transfer buffer bounds resident copying, while temporary disk scales with source DB size; this is not the backup512MiB cap. No source SQL connection or original permission repair occurs.

The gate precedes business work, not all filesystem or Desktop OS activity. Old code can acquire a lock, create WAL/SHM, read token/config or validate media tools before failure. Arbitrary same-user/root SQL edits, dropping triggers, replacing files and unsupported code that bypasses `openStore` are outside the existing storage threat model. Do not market this as a security sandbox or universal downgrade compatibility.

SQLite's documented main-schema triggers and `RAISE(ABORT)` support this design, but the exact duplicate `INSERT OR IGNORE` behavior remains an implementation proof gate on Node and bundled Electron SQLite. After old-open failure, compare all original SQL values and schema/gate definitions and inspect/reopen any WAL/SHM. Later `beb7fcf`/`1536878` entrypoints must close their acquired SQLite handle and release their own lock before child exit. The earliest `3446aed` entrypoint lacks that failure cleanup: evidence must report its handle/lock retention until process exit rather than changing frozen source or deleting a stale lock to bypass refusal. Business startup must still fail before downstream execution, and the closed DB must remain logically intact and reopenable afterward. Old journal-mode PRAGMAs can change file-header bytes before refusal; whole restored-DB hash equality is not the guarantee. No change to trusted_schema or native security policy is permitted. Sources checked 2026-10-12: [CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html), [trusted_schema](https://www.sqlite.org/pragma.html#pragma_trusted_schema).

## 5. Fresh-action and transport contract

Retain domain input shapes, request IDs and hashes. Do not prefix/replace captured keys, insert current origin into old JSON, or alter historical ACK payloads.

For restored-only effectful calls, use the outer invocation context `expectedWorkspaceOrigin`. HTTP RPC body becomes `{operation,input,expectedWorkspaceOrigin}` when explicitly provided. Strict UUID parsing; domain input still uses its existing strict schema. The SDK takes this through call options, never guesses it after reconnect. Normal calls without this field keep current wire behavior on normal workspaces.

- Renderer pins origin when a **new explicit gesture** creates its draft/pending intent, and persists it with that intent. Old session entries lacking/mismatching origin stay held; no automatic adoption or new key. Project ID alone cannot distinguish the original and clone.
- CLI requires an explicit `--workspace-origin` for effectful restored calls. MCP can pin the same explicit option at process launch; it must never rediscover/update origin on backend reconnect. This keeps ordinary tool argument schemas intact. A dedicated non-creating `workspace.restore.inspect` returns the non-secret current origin, profile, bounded held counts and supported-operation reasons. It has no filesystem path or model-content authority, and is not added to the built-in Agent catalog.
- Origin is a mismatch guard, not a bearer credential, paid approval or proof of a physical human click. Existing authenticated callers intentionally starting fresh allowed local work retain that authority. They cannot use a new outer origin/key to release any captured task or approval.
- Business entrypoints and special HTTP task routes validate the same backend-owned profile/context. UI hiding is not enforcement. Direct shared-service consumers use the same gate.
- Exact valid historical receipts can still be disclosed after existing ownership checks, without scheduling or origin insertion; changed key reuse remains conflict. Captured pending intent/proposal key without a receipt is held before invoking a mutator. Uncertain state is never probed by a mutator.
- New durable edits bind the validated origin in their existing prepare transaction. Execute/reconcile/acknowledge target only current-origin rows; startup receipt-only reconciliation skips all captured rows. Nested `services.call` receives a backend-owned context derived from that exact persisted task/input binding, not an automatically current-stamped store context. New acknowledged outcomes remain monotonic under races.
- New exports bind origin in the existing acceptance transaction. The worker selects positive current origin before LIMIT and checks the immutable export/snapshot binding again at claim, pre-media, after await, publication, failure and cleanup. Pre-acceptance capability callbacks retain the caller's validated immutable invocation context; after acceptance they use the persisted export binding. Startup requeues only new-origin exports.
- Keyless existing operations retain existing non-idempotent limitations and never auto-retry. Async import binds current origin/project/name/MIME/content hash for that call and rechecks around file write, ffprobe and DB publication. This slice does not invent an import transaction ledger.
- Explicit preflight/capability computation uses the same fresh-action context, existing bounded media lifecycle and revision/source fences. Advisory readOnly metadata is not an execution permission.

## 6. Service composition and UI

Restored startup must avoid constructing disabled services: current `services.mjs:113–115` image/frame/waveform constructors reconcile rows, server startup constructs settings/connectors/chat, and `jobs.mjs:95–98` normalizes old statuses. Use a verified-profile composition branch and shared pure readers, not a flag supplied by HTTP or a constructor that mutates first and rejects later.

The worker profile is export-only. Both automatic and manual ticks skip all video jobs and captured exports. Disabled API/CLI/MCP calls produce the same structured `RESTORE_OPERATION_UNAVAILABLE` or `RESTORED_RECORD_HELD` reason. Settings/approval routes cannot bypass it. Restriction errors are not `not_applied` proof for an old unknown outcome.

The right workspace shows a compact restored-branch banner, restored-branch creation time, allowed functions, held-work count and expandable explanation. `createdAt` is the branch creation time; it must not be presented as the source capture time. The source backup ID is available in details. Task rows retain their original status and add an explicit held label. Pending indicators for current new work exclude historical holds; total history remains visible. Disabled generation/Agent/Comfy/frame/waveform buttons explain why and do not issue hidden startup calls.

Legacy `project.get` and `timeline.get` can create a default timeline. Restored startup needs a noncreating read projection for absent timelines; initial creation occurs only in a freshly admitted explicit edit. Verify the empty-state renderer contract instead of silently substituting an unsaved timeline. Existing normal-workspace wire behavior stays unchanged.

History viewers must not initialize executing runtimes to read old rows. Existing task/result links may read local saved files only after ownership validation. There is no staged-result recovery, remote observation, approval release, reauthentication shortcut or hidden retry in v1.

## 7. Migration and follow-on route

Initial import supports only classified schema24 backups. Older schema sources require a separately specified offline upgrade; do not run their normal worker or silently accept a lower max version. Schema25 backups must be explicitly supported by backup create/verify before advertising a new backup of restored work. Chained restore requires minting a new origin, retaining all previous restoration archives and treating every copied operation as captured; it is not automatic v1 support.

**Parent decision: restored schema25 backup.create is explicitly unavailable in v1.** UI and CLI must explain this before attempting capture and must not create a misleading second-generation backup that cannot be restored. Do not widen create/verify to emit or accept a new backup profile in this slice. The existing verified original backup remains untouched; a generic archive/export feature is outside scope. A later bounded change must enable create/verify and recursive restore together, preserving previous origin/history chains. This limitation must be prominent before the user chooses to work in the restored branch.

Enable additional families in later bounded increments: (1) new local frame/waveform attempts with current-origin admission; (2) new provider/image/Comfy work with fresh explicit settings/review/consent and group/quota rules; (3) new Agent conversations/proposals with epoch-qualified active-run index and context provenance. These enable **new** work only. Releasing captured unknown/submitted work would require a separate provider-specific proof and approval design, and is not promised.

## 8. Ownership and staged implementation

After parent contract approval, use one new worktree based on beb7fcf with three bounded parallel lanes plus an independent read-only reviewer:

1. **Storage/schema:** new restore contracts/storage/schema modules, `db.mjs` bootstrap branch, offline CLI and exact preservation/crash/legacy-gate fixtures. Own all schema/index/trigger edits and the explicit restored-profile backup refusal.
2. **Execution:** narrow restore policy/context module, services composition, edit-task epoch handling, direct captured-key guards, export producer/worker fences, non-RPC server route gates. Reuse every existing business mutator/renderer.
3. **Clients/UI:** SDK outer context, CLI/MCP explicit origin pinning/discovery, renderer recovery identity and compact right-workspace/task-center restriction UI, guides/API/Skill. Do not duplicate business execution.
4. **Independent review:** exact schema delta/preservation, entire route/constructor/worker inventory, stale-origin and old-runtime adversarial matrix; no source ownership overlap.

Gate A before UI integration: contract + schema preservation + old-runtime refusal + no inherited execution. Gate B: real HTTP/CLI/official MCP fresh edit/replay/held denial and same-project pending-lane coexistence. Gate C: fresh builds, Linux packaged restore → import/edit/undo → preview/export → normal exit/reopen with source/backup/hash proof. Then source freeze and parent full aggregate. Do not merge a partially safe restore into main between these gates.
