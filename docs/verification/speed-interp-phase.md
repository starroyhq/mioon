# SP-I0：曲线变速下的光流补帧相位原型

原型卡，不接产品行为、不改项目格式、不加依赖。脚本在
`scripts/speed-interp-phase/`，可重跑；合成素材全部由脚本生成。

## 1. 曲线光流的相位

### 现状与内部精度

FFmpeg 7.1.5 `vf_minterpolate.c` 的 `interpolate()` 先把输出 PTS 换算成相邻两帧输入 PTS
之间的整数 alpha：

```text
pts   = av_rescale(out_pts, 1024 * out_tb.num * in_tb.den, out_tb.den * in_tb.num)
alpha = (pts - in_pts1 * 1024) / (in_pts2 - in_pts1)      # integer truncation, clip 0..1024
```

- alpha 精度是源帧区间的 **1/1024**，不是连续实数；`alpha == 0/1024` 直接复制源帧。
- 两帧输入之间 alpha 只能线性变化：输入 PTS 被改写为共享映射的反函数后，滤镜实际给出的是
  **源帧间线性插值的反函数**，不是 PCHIP/共享映射的连续反函数。
- 曲线内部慢速区一帧源帧间隔包含多个输出帧时，量化步长为 `interval/1024`；快速/近 1× 区间
  每个源帧间隔少于或接近一个输出帧，量化更大。

### 实测方案：按共享映射分配源帧 PTS

把每个源帧 n 的输入 PTS 设为共享映射在整数源位置 n 的反函数（输出时钟），再用
`minterpolate=fps=30`；`phase.mjs` 用共享合同 `compileTimeMap`/`timeMapSourceAtOutputFrame`
计算目标相位，`empirical.mjs` 用无损 NUT 单帧 + concat 以 1/90000 时基送入同一 FFmpeg 7.1.5，
用交替灰阶帧反推 alpha 并与 7.1 源码公式逐帧比较。

本机（macOS arm64，M3 Max，FFmpeg 7.1.5）结果：

- 参考曲线（0.1×→0.8×→2×，601 输出帧）慢速有效帧 598：相位误差
  max **0.00147** 帧、p95 **0.00095** 帧、mean **0.00036** 帧。
- 逐帧 alpha 公式匹配 **597/600**；剩下 3 帧是末尾源端点钳位/8 bit 混合舍入，内部 597/597 全匹配。
- 5 条不同曲线（0.1×–2× 组合）在“慢速有效帧、去掉尾部源端点”上的 bound：
  `reference 0.00147`、`symmetricSlow 0.00381`、`nearOne 0.00300`、`sharp 0.00610`、
  `slowFastSlow 0.00546` 帧。
- 对每条源帧区间独立最优线性拟合的下界是 0.00085 帧（参考曲线），说明剩下的误差主要来自
共享曲线与分段线性 PTS 的差异 + 1/1024 量化，而不是实现 bug。

### 版本化量化方案建议（`interp-phase-pts-v1`）

1. 编译时按共享映射把源帧 PTS 量化到有理输入时基；
2. 逐曲线、逐可见输出窗口计算上述绑定，**只统计真正应用光流的慢速有效帧**，排除尾部端点；
3. 在 profile 里记录 `maxPhaseErrorFrames`，超过协调人确定的 epsilon 就拒绝该曲线的光流，
   不静默使用近似。按本机数据：
   - epsilon = 0.005 帧：`sharp` 曲线（0.0061）会被拒绝，其余通过；
   - epsilon = 0.01 帧：全部通过，但接近 1× 的曲线精度依赖实际输出窗口。
4. 该 bound 是**逐曲线**的，不是通用常量；曲线点集/源/输出时基变化都要重算。

**结论：** 不改滤镜时，曲线的光流相位只能做到“分段线性近似 + 1/1024 alpha 量化”。
这不是精确等价；可以用上面的版本化 bound 门槛控制，但需要明确接受误差或改滤镜。

### 固定构建做不到精确时可选方案

| 方案 | 做法 | 成本/风险 | 备注 |
| --- | --- | --- | --- |
| A. 版本化近似（本原型） | 按共享映射分配 PTS，编译期算 bound 并拒绝超限曲线 | 0 依赖；实现 1–2 人天；有明确相位误差 | 需要协调人定 epsilon；`sharp` 类曲线可能不可用 |
| B. 补丁/自带相位滤镜 | 给 7.1 minterpolate 增加“目标 alpha 侧数据/输出帧相位表”，纹理合成仍用原算法 | 4–6 人天 + 构建/发布/哈希重做；不改变产品算法风险 | 相位可到 1/1024，最符合“共享合同唯一时间依据” |
| C. 每个输出帧单独调用滤镜 | 每次固定一对源帧、按 1/1024 量化选择 alpha | 正确性可验证；成本约 O(输出帧数) 次滤镜启动，生产不可接受 | 只能做交叉验证/小样 |
| D. 只允许恒定/线性速度段光流 | 编译时只开放相位 bound 很小的小段 | 成本最低，功能退化为分段光流 | 曲线产品承诺会明显缩水 |

## 2. 帧混合直接消费连续坐标

`framerate=fps=30:interp_start=0:interp_end=255` 的权重由输入 PTS 计算：

```text
work_pts = start_pts + n * (1/fps) 换算到输入时基
w        = round((work_pts - pts0) * 128 / (pts1 - pts0))   # 7 bit blend factor
dst      = (src0 * (128-w) + src1 * w + 64) >> 7
```

原型用同一份共享映射 PTS 与交替灰阶帧逐帧验证：参考曲线 **600/600** 帧权重公式匹配，
常速控制 600/600；不是先按“关”的选帧表丢帧/重复再混合。方向由窗口内源帧顺序表达
（倒放窗口反转帧序，权重仍作用在顺序上的下一帧），不需要给混合权重加方向符号。

限制：`framerate` 只有 7 bit 权重，且同样按输入 PTS 分段线性消费；参考曲线实测相位误差
p95 约 **0.0040** 帧、max 约 0.0053 帧（尾部另计），比 minterpolate 的 1/1024 量化粗。
混合若用于曲线，必须和光流一样按上述 per-curve bound 控制，不能直接假定与共享映射等价。

## 3. 像素格式准入

用 `-noauto_conversion_filters` 关闭自动转换，逐个直接喂 `minterpolate`：

- **直接接受（首期 8 bit planar 清单）**：`yuv410p, yuv411p, yuv420p, yuv422p, yuv440p,
  yuv444p, yuva420p, yuva422p, yuva444p, gray`；`yuvj420p/yuvj422p/yuvj444p` 也在滤镜列表，
  但它们是受限范围 YUVJ 输入，首期不纳入源域准入（由 colour 链决定）。
- **直接拒绝**：`nv12, p010le, gray10le, gray16le, yuv420p10le, yuv420p12le, yuv444p16le,
  yuva420p10le, gbrp, gbrp10le, rgb24, rgba, gbrpf32le`。拒绝原因统一是
  “filters … do not have a common format and automatic conversion is disabled”。
  默认开自动转换时这些输入都会被**静默转成 8 bit** 后成功，所以产品必须在进入滤镜前按
  optical profile 明确拒绝，而不是依赖自动转换。

结论：首期 optical 只准入明确 8 bit planar 源域；10 bit / RGB / float 给出明确不可用原因，
禁止自动降 8 bit。

## 4. 量测

合成 1080×1920 / 30 fps / 150 源帧（5 s），0.25× → 600 输出帧。包含端点补帧并裁到 600；
x264 veryfast/CRF23/bf0/g60/yuv420p，2 编码线程、1 滤镜线程。本机 M3 Max / FFmpeg 7.1.5：

| 档位 | 墙钟 | CPU user | RSS | 输出大小 | 帧数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 关，重复帧 | 1.954 s | 3.52 s | 295 MiB | 5.41 MiB | 600 精确 |
| 帧混合 framerate | 2.246 s | 4.81 s | 316 MiB | 10.93 MiB | 600 精确 |
| 光流 minterpolate | 83.088 s | 84.39 s | 886 MiB | 8.91 MiB | 600 精确 |

光流约是关的 **42.5×** 墙钟；单任务 1 GiB 预算下 886 MiB 已接近上限，需单任务/后台处理。
CI 的 macOS arm64 步骤会把同一 JSON 写入 `checks-sp-i0` artifact，补齐方案 §4 缺的 CI 数据。

合成样本（320×180，120 fps 解析真值用作 0.25× 的 ground truth）：

- 切场（红→蓝，切点在源帧 29/30）：`scd=fdiff:scd_threshold=10` 时切场邻域 9 帧中
  **0 帧**跨场景（都等于切点某一侧源帧）；`scd=none` 时 3 帧出现跨场景估计。
- 遮挡样本（移动方块经过静态遮挡条）：输出帧 vs 120 fps 真值平均 |Y| 误差，
  帧混合 **0.667**、光流 **0.132**；四分之一相位帧混合 **1.062**、光流 **0.201**。
- 快速运动样本：帧混合 **0.751**、光流 **0.150**；四分之一相位 1.219 / **0.214**。
  这说明该合成运动上光流更接近真值，但不外推到真人/毛发/字幕边缘。

## 5. 分块可行性

按方案 §3.4 的 2 秒源块（60 源帧）、前后各 2 源帧重叠上下文、每块只保留自己拥有的输出帧：

- 180 源帧 → 720 输出帧，切成 3 块；owned 720/720，missing 0，重复 0；
- 每块输出的 owned 帧与不切块整段输出**逐字节相等**（720/720 byte-identical）。
- 说明在当前固定构建下“重叠上下文 + 只输出自己拥有的帧”的块边界不重复不缺帧；
  这是用 64×64 合成样本对滤镜边界的证据，不代表长片性能/内存已验证。

## SP-I 建议

1. **曲线光流先不直接上线。** 不改滤镜时它只能是版本化近似 + per-curve bound；
   推荐 SP-I 二选一：
   - 若要“共享合同唯一时间依据”成立，选方案 B（补丁 minterpolate 接收目标 alpha 侧数据），
     估 4–6 人天 + FFmpeg 构建/发布/哈希工作；原型确认纹理合成部分可复用，改动集中相位入口。
   - 若不做构建改动，选方案 A，epsilon 建议 **0.005 帧**（sharp 类曲线拒绝），并在 UI/任务状态
     明确“该曲线不支持光流”，不要静默降级。
2. **帧混合**可直接消费共享连续坐标，但 7 bit 权重、同样的 per-curve bound；若用于曲线，
   和光流共用编译期 bound 检查。
3. **像素范围**：首期只准入 8 bit planar optical profile；10 bit/RGB/float 在写最终文件前
   明确拒绝，禁止自动降 8 bit。
4. **量测/预算**：光流约 42× 墙钟、886 MiB RSS，必须后台单任务、按源窗口/输出块缓存，
   导出复用已确认代理，缺代理给原任务状态；CI 数据已由本卡路径门禁步骤补。
5. **分块**：2 秒源块 + 2 源帧重叠 + 只输出 owned 帧，在当前构建下边界精确；长片、真实
   素材和 8 GiB 设备预算仍需 SP-I 实测。
6. **要用户定的事**：① 接受版本化近似（epsilon 取 0.005/0.01）还是批准改 FFmpeg 构建；
   ② optical 首期范围是否只 8 bit YUV planar；③ 光流后台时间/内存预算与是否允许单任务
   排队；④ CI 是否长期保留 macOS arm64 media-tools 下载步骤（每次约 25–50 MB 下载）。
