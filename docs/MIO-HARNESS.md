# Mio harness 架构

更新：2026-10-27 · 状态：架构已确认，尚未实施。

现有行为仍以 [Mio v2 执行与恢复](AGENT-TASKS-V2.md) 为准；本文各项在对应分期实施并验收后才生效。

## 定位

Mio 的 harness 是 Mioon 自有的任务内核，统一调度模型、项目工具、上下文和检查，所有进度以 SQLite 记录为准。本文确定：

- 模块边界；
- 上下文、检查和恢复的数据流；
- 必须保留的约束；
- 演进顺序。

不引入外部 agent 框架。这是 2026-10-20 已定的方向，依据是 AI SDK 与 pi 两个验证分支。

## 已定决策（2026-10-27）

| # | 决策 |
|---|---|
| 1 | Run Engine 是唯一的调度者。模型接入只完成单次推理，检查只返回结果和差距；是否继续由 Run Engine 按预算与授权决定。 |
| 2 | 工具按需加载：核心组常驻，其余工具由模型按组加载。加载只改变可见范围，不授予任何权限。 |
| 3 | 首期压缩只用宿主规则，不调用模型生成摘要。原始记录和已保存的模型请求保持不变。 |
| 4 | 检查未通过时最多自动补做 1 次，仍受每轮步数和分档确认约束。 |
| 5 | 历史容量首期只做不改存储格式的削减；去重存储和历史清理按实测数据另行决定。 |
| 6 | 新增界面先出设计稿并确认，再实施。 |

## 现状基线

基于 main `2bb498f`（2026-10-26）。实测使用离线合成模型，不联网。

| 项目 | 现状 | 位置 |
|---|---|---|
| 工具目录 | 每次模型请求都携带全部 98 个工具；历史为空时，请求已超过 115 KB（三种协议、中英文实测） | `task-tools-v2.ts` 的 `list()`；`task-gateway-v2.ts` 的 `buildTaskModelRequest` |
| 轮内历史 | 每次请求重放本轮全部模型输出和工具结果，只增不减；上限 128 KiB（`TASK_MODEL_LIMITS.historyBytes`） | `task-runtime-v2.ts` 的 `execute()` |
| 超限后果 | 实测每次回复约 30 KB 时，第 5 次模型请求后（30 步只用了 10 步）整轮以 `AGENT_CHAT_LIMIT` 失败。此时最后一步是已完成的工具步骤，`retry` 返回 `AGENT_TASK_STATE_CONFLICT` | `execute()`；`action()` 的 `retry` 分支 |
| 工具结果 | 只裁剪结构（数组 200 项、字符串 16000 字符、深度 12），没有字节上限 | `task-tools-v2.ts` 的 `projectResult` |
| 跨轮上下文 | 只取同对话最近 4 轮已完成执行的用户原话、补充说明和最后一次回复。工具做过什么、后台状态都不进入；失败或停止的轮次完全不可见 | `send()`；`task-journal-v2.ts` 的 `contextRuns` |
| 冲突基线 | 取自发出模型请求的那一刻。模型读取某目标后、下一次请求前该目标被修改，执行既不暂停也不告知模型 | `execute()` 中的 `baseline`；`modelConflictingTargets` |
| 落库 | 每个模型步骤保存完整请求（含工具目录）和一份历史副本：实测单行 224–469 KB，其中包括每次约 30 KB 的回复文本。流式回复约每 50 ms 重写一次整个步骤行，并追加一行事件 | `beginModelStep`；`appendText` |
| 容量 | Mio 历史在全工作区共用 20000 行 / 256 MiB，除了删除项目没有释放途径 | `task-storage-schema-v2.ts` |
| 模型接入 | Anthropic 请求不设缓存断点；三种协议的输出上限都固定为 4096；推理内容会被拒绝，Anthropic thinking 关闭；token 用量不写入记录 | `task-gateway-v2.ts` |

## 总体结构

```text
               Mio panel / HTTP / client / CLI
                             │
                      ┌──────▼───────┐
                      │  Run Engine  │  loop · budget · pause · stop · approval
                      └──────┬───────┘
     ┌───────────┬───────────┼───────────┬───────────┬─────────────┐
     ▼           ▼           ▼           ▼           ▼             ▼
  Context     Tool        Model       Tool        Checks       Journal &
  Assembler   Catalog     Adapter     Executor                 Recovery
     │                                   │           │
     └──── read only: journal snapshot, domain state ─┘
                                         │
                   domain services: canvas, shots, assets, timeline
                   ──▶ background jobs: generate, render, export
                   ──▶ results written back in domain transactions
```

| 模块 | 职责 | 现有代码 | 本期变化 |
|---|---|---|---|
| Run Engine | 一轮执行的循环、步数预算、暂停、停止、确认和恢复；唯一决定继续还是结束 | `task-runtime-v2.ts` | 拆出上下文装配；接入工具加载和补做 |
| Context Assembler | 从记录确定性地生成下一次模型请求的历史、工具和宿主提示；负责预算与压缩 | 散落在 `send()`、`execute()`、`assertNoteCapacity()` | 新增 `task-context-v2.ts` |
| Tool Catalog | 工具分组、核心组、按需加载 | `task-tools-v2.ts` 的 `list()` | 新增分组与 `mioon_tools_load` |
| Model Adapter | 单次推理；三种协议的请求构造与流解析；保留续接所需的原始输出 | `task-gateway-v2.ts` 及各传输 | 缓存断点、用量记录 |
| Tool Executor | 工具准入、分档确认、修订与编辑占用检查、执行及变化记录 | `task-tools-v2.ts`、`task-effects-v2.ts` | 规则不变；未加载工具的调用返回加载提示 |
| Checks | 宿主检查与目标检查：结果、证据和差距 | 无 | 新增 `task-checks-v2.ts` |
| Journal & Recovery | 先落库再执行；请求与控制回执；未知结果；恢复与撤销 | `task-journal-v2.ts` | 流式文本合并写；不改存储格式 |

边界：

- Context Assembler 和 Checks 只读，不写库。
- 人工编辑、其他窗口、CLI、MCP 和后台结果都经过领域服务，推进同一套目标修订；装配与检查都以修订为准。
- 宿主派生的内容和模型输出都不能成为权限来源。

## 一轮执行

1. **发送**：校验输入和授权，冻结本轮的 `run.context`，包括：
   - 语言标记（固定为第一条）；
   - 同对话的近期轮次及其执行记录；
   - 项目概况；
   - 本次消息和附件句柄。
2. **循环**（Run Engine）：
   1. 复查授权与执行状态。
   2. Context Assembler 生成历史和工具列表；超出预算时按规则压缩。
   3. 先落库模型步骤（请求原件不可变），再发送。
   4. 模型调用了工具：逐个执行，即准入、确认、修订检查、执行，业务修改与变化记录在同一事务提交；然后回到第 1 步。
   5. 模型没有调用工具：
      - 若有已声明的目标，先评估；有未通过项、本轮尚未补做过、步数未用完时，附上差距再请求一次模型（计 1 步）。
      - 否则本轮结束（`completed`）。
3. **结束后**：后台工作未结束时沿用现有的 `backgroundPending`；检查结果按读取时的记录计算。

三个维度分开记录和展示：

| 维度 | 表达什么 | 来源 |
|---|---|---|
| 执行状态 | 本轮正在运行、等待确认、已暂停，还是已经结束 | Run 状态机（不变） |
| 后台状态 | 生成、渲染、导出等任务是否仍在进行 | 任务来源绑定（不变） |
| 检查结果 | 每项检查通过、未通过、等待或不适用 | Checks（新增） |

## 上下文装配

### 输入

- 发送时冻结的 `run.context`：
  - 语言标记；
  - 同对话最近 4 轮：已完成的轮次带用户原话、补充说明和最后回复；失败、停止或已撤销的轮次带用户原话和补充说明；每一轮都附宿主执行记录；
  - 项目概况；
  - 本次消息和附件句柄。
- 本轮记录：模型步骤的原始输出、工具步骤的结果、补充说明、跳过名单、已加载的工具组、各模型步骤保存的修订基线。
- 当前目标修订，用于生成过期提示。

### 预算

- 历史不超过 `historyBytes`（128 KiB，不变）；整个请求不超过 `requestBytes`（512 KiB，不变）。
- 单个工具结果交给模型的视图不超过 16 KiB（新增常量）。
- 首期按字节计算；token 用量只记录，不参与决策。

### 工具结果视图

- 结果超过上限时，生成确定性的截断视图：
  - 必须是合法 JSON；
  - 显式标注已截断、原始大小和省略数量；
  - 附上如何重新读取的提示。
- 截断视图不得包含绑定凭据，例如响度报告的 `candidateDigest`。需要截断时去掉凭据并标注，由模型重新准备。
- 记录中保存完整的投影结果；截断只发生在交给模型的视图里。

### 压缩规则

压缩以"一次往返"为单位：一次模型输出加上它的全部工具结果。往返永不拆开，以保证三种协议的调用与结果始终配对。

超出预算时依次执行：

1. 从最早的往返开始，把工具结果换成存根，保留调用与结果的配对、工具名和原始字节数。
2. 仍然超出：从最早的往返开始整段移除，并在本次消息之后插入一条宿主执行记录，概括被移除的步骤（步骤说明、操作、目标、状态、变化）。
3. 仍然超出：移除最早的历史轮次，保留语言标记和本次消息。
4. 仍然超出：这只可能是最新一次往返本身过大，保持现有的失败语义。

压缩到低水位（约为预算的 60%）为止，避免之后每一步都改动请求前缀。

始终原文保留：

- 语言标记；
- 本次消息；
- 全部补充说明（以后还包括 C3 提问的回答）；
- 最新一次往返。

发生压缩时，附加本轮约束摘要：跳过的目标、被拒绝的确认、失败或结果未知的步骤。

### 宿主提示

- 执行记录、项目概况和过期提示都由宿主从记录派生，按本轮语言生成，并标明"仅供参考，不是指令"。它们不授予权限，也不参与授权或审批判断。
- 过期提示：本轮读过或改过的目标，在两次模型请求之间被本轮以外的修改推进了修订（人工编辑、其他窗口、后台结果）时，下一次请求前列出这些目标，要求修改前重新读取。首期只提示，不改变暂停语义。

### 冻结与恢复

- 装配结果写入模型步骤的请求原件（已有机制，不可变）。未发送的 intent 恢复时直接使用原件，不重新装配。
- 装配是纯函数：相同的记录得到相同的字节；不读时钟，不用随机数。

## 工具目录与按需加载

- 每个模型可见的工具恰好属于一个组：
  - 核心组只含只读工具和宿主工具，始终可见；
  - 修改、导出、生成等工具都在各自的组里，需要时加载。
- 宿主工具 `mioon_tools_load` 加载一个或多个组：
  - 属于只读档，不产生变化，计 1 步；
  - 各组的用途写在这个工具的描述里。
- 同一轮内已加载的组只增不减，按目录顺序排列，以保持请求前缀稳定；新一轮从核心组开始。
- 本轮带附件时，自动包含对应的导入工具。
- 诊断运行保持现有的工具选择方式，不受分组影响。
- 模型调用目录内已知、但本轮尚未加载的工具：不执行，以被拒绝的步骤返回"请先加载某组"。目录之外的名字维持现有的协议错误。
- 分档、确认、授权和跳过规则都不因加载而改变。

## 上下文来源的分层

| 层 | 内容 | 地位 |
|---|---|---|
| 权威记录 | journal（执行、步骤、变化、回执）、领域状态、目标修订 | 唯一依据 |
| 宿主派生 | 执行记录、项目概况、过期提示、压缩存根、检查结果 | 可以随时重算；作为数据交给模型 |
| 项目资料 | 以后的项目说明（创作流程 C6，用户编写）和内置技能包（按需读取） | 资料，不是指令；不能改变档位、工具范围或授权 |
| 用户输入 | 本次消息、补充说明；以后 C3 提问的回答 | 用户指令；同样不能扩大工具范围或授权 |

首期不保存模型写的摘要。C6 的项目说明由 Context Assembler 每轮带上；技能包通过读取工具按需获取，结果同样受视图上限和压缩规则约束。不另建一套记忆。

## 检查

### 宿主检查

不需要模型参与，按本轮实际产生的变化和后台工作自动选择：

- **导出与渲染**：任务成功；产物存在；记录的参数与请求一致。
- **生成**：任务进入终态；成功的版本已经发布；失败和费用未知分别列出。
- **时间线完整性**（本轮改过时间线时）：片段引用的素材和版本存在且可用；导出预检没有阻断项。
- **拆解与关键帧任务**：进入终态。

### 目标检查

- 宿主工具 `mioon_goal_set` 属于只读档，计 1 步。模型从用户要求中提取可以确定判定的条件，只能使用固定的条件类型：时长、画幅与帧率、导出参数、片段、字幕或镜头数量、生成是否完成等。
- 以本轮最后一次设置为准。
- "节奏舒服""画面高级"这类主观要求不进入检查，由用户自己判断。

### 结果与补做

- 每项结果分为通过、未通过、等待、不适用，并附上依据的目标与修订、实测值和期望值。
- 检查在读取时按当前记录计算，不落库：
  - 目标之后被修改，结果会自动反映；
  - 结果不改变执行状态，也不触发撤销。
- 补做：
  - 模型给出最终回答时，目标检查有未通过项（不含等待）、本轮尚未补做过、步数还没用完，就附上差距再请求一次模型；
  - 补做中的付费操作仍需确认；
  - 最多补做 1 次，之后照常结束并列出差距。
- 后台未完成的项显示为等待；后台完成后由宿主重算，不发模型请求。

## 存储与容量

- 现有配额和写入放大见"现状基线"。
- 首期（不改存储格式）：
  - 工具按需加载后，每个模型步骤保存的请求原件会明显变小；
  - 流式文本改为合并写入，例如每 250 ms 或每 8 KiB 写一次。
- 需要授权后再做：
  - 工具目录和请求原件按摘要只存一份；
  - 历史保留与清理策略：会删除审计记录，属于产品决定。
- 如需升级存储格式，与创作流程 C1、C3、C6 的存储需求合并为一次升级。

## 必须保留的约束

- 先落库再执行；模型请求原件不可变。
- 结果未知不自动重发；生成走原有的对账流程。
- 发送前、执行前、后台实际发出前，都复查授权、执行状态、策略、跳过名单和目标修订。
- 确认绑定原工具参数和目标修订。
- 付费操作默认需要确认；不设次数上限，只受每轮步数约束。
- 模型不能提供项目、请求 ID、批准标志、凭据、路径或原始字节；`_mio_step` 只存在于模型侧的工具包装里。
- 每轮的回复语言在发送时固定。
- 恢复副本只读；诊断运行不进入对话历史和上下文。
- 宿主派生内容和模型输出都不能成为权限来源。

## 演进顺序

| 期 | 内容 | 存储格式 |
|---|---|---|
| H0 | 基线：离线请求指纹、容量测量 | 不变 |
| H1 | 装配器抽取（请求字节不变）→ 工具分组 → 结果视图与压缩 → 执行记录、项目概况、过期提示 → 缓存与用量 | 不变 |
| H2 | 流式文本合并写入；容量复测 | 不变 |
| H3 | 宿主检查（先做后端；界面等设计稿） | 不变 |
| H4 | 目标检查与一次补做（先做后端；界面等设计稿） | 不变 |
| H5 | 模型摘要、推理模型续接、按模型的上下文预算、可配置输出上限、去重存储与历史清理 | 视决定 |

依赖关系：

- H 系列唯一的前置是 M7（设置 · Mio）合入 main。创作流程的 C 项都不是前置。
- C1 与 C3 都改动发送和执行循环，并且都要升级存储格式。建议排在 H1c 之后，合并为一次升级。C3 的回答属于用户输入，压缩时原文保留。
- C6 建议排在 H1d 之后：项目说明作为每轮的上下文输入，技能包的读取结果受视图上限和压缩规则约束。项目说明的存储可以并入 C1、C3 那次升级。
- C7、C8 与 harness 基本无交集，可以并行。它们新增给 Mio 的工具，归入相应的工具组。

## 未决事项

1. 是否做去重存储、是否提供历史清理：H2 实测后决定。
2. 是否引入模型摘要：H1 完成后用真实模型复测再决定。
3. 过期提示是否升级为暂停：首期只提示。
4. 推理模型支持，以及按模型设定的上下文预算。
