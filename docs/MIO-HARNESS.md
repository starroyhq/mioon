# Mio harness：当前执行、记录和计量

更新：2026-11-02。H1–H4、流式检查点和 X 线能力已实施；本分支包含 R1 的记录、运行时及用量/存储计量。R1 的合并仍须等待 S0 P4，合并前重新取最终 main 并验证。规范文件与界面不属于本轮实现。

执行与恢复约定见 [AGENT-TASKS-V2](AGENT-TASKS-V2.md)，记录格式见 [MIO-RECORDS](MIO-RECORDS.md)。本文描述当前代码，历史的 2026-10-26 全目录请求、逐 delta 复制事件和容量基线不再作为现状。

## 职责与边界

| 模块 | 当前职责 | 主要实现 |
|---|---|---|
| Run Engine | 唯一决定继续、等待、暂停和结束；持有预算、取消、授权与修订围栏 | `task-runtime-v2.ts` |
| Context Assembler | 根据冻结来源生成模型视图，预算、裁剪和压缩均确定 | `task-context-v2.ts`、`mio-assembly.ts` |
| Tool Catalog | 核心工具常驻，其余按名称加载；加载只改变可见范围 | `task-tool-groups-v2.ts`、`task-tools-v2.ts` |
| Model Adapter | 单次三协议请求与流解析，保留原输出块及被报告的用量 | `task-gateway-v2.ts`、协议传输、`task-usage-v2.ts` |
| Tool Executor | 校验来源能力、参数、确认、目标修订与编辑占用；业务修改和变化证据共事务 | `task-tools-v2.ts`、`task-effects-v2.ts` |
| Checks | 宿主检查、目标检查与最多一次补做的差距输入 | `task-checks-v2.ts`、目标/检查模块 |
| Journal & Recovery | 规范 entries、步骤、请求版本链、控制回执、未知结果和撤销 | `mio-journal.ts`、`mio-records.ts` |
| 只读计量 | 每轮用量及每项目完整存储清单，不调用模型或写入 | `mio-run-usage.ts`、`mio-storage.ts` |

没有第二套执行引擎。真实内核项目通过登记的连接身份选择新 journal；S0 切换前旧工作区执行路径保持原行为，用量仅增加只读适配，不扩展旧工作区迁移。应用库的设置、发送授权和全局 policy 不附加到项目连接；policy CAS 与回执复用 S0 的应用端口。

## 一轮如何执行

1. **接受发送。** 校验项目归属、模型设置版本和 `project_agent` 授权，固定本轮语言、配置、用户消息、附件和上下文来源，先持久保存 run/entry 身份。诊断与普通对话隔离。
2. **装配。** 外层 collector 在一致读取边界收集规范 entries、目标 baseline、工具 schema 与有效协议包装。纯函数只读传入的不可变值，返回确切 body、字节数和 hash，不读实时 DB/文件/目录、不生成 ID 或时间。
3. **先记 intent，再派发。** 请求保存原件、装配版本和来源清单；实际提交前复查状态、发送授权、付费确认、目标修订和跳过规则。已越过派发边界不能被当作未发送。
4. **接收模型输出。** 文本按 8 KiB 或 250 ms 合并写检查点，尾部停顿由计时器刷新。完整合法响应归档、步骤完成、partial 清除、成功原件清除及用量小投影在同一事务内完成。
5. **执行工具批。** 每项调用仍要经过来源请求冻结 schema 的准入、参数校验、确认和修订围栏。当前目录加载或后来的设置变化不能扩大旧来源的权限。领域写入与 Mio 结果/变化记录共用业务事务。
6. **决定下一步。** 有待批准、问题或未知结果则交还用户；否则继续模型往返。最终答复后若目标存在可确定的未通过项，预算允许时最多补做一次，仍计步并受原授权/付费确认约束。
7. **结束与关闭。** 执行状态、后台工作和检查结果分别表达。宿主中断请求/SSE/执行器，再等待全部排空，最后关闭自己持有的 store；关闭不能触发自动重发或迟到写入。

模型输出、宿主观察和工具结果都不是权限来源。补充说明、回答与拒绝按各自用户动作记录，不能因为文本相同而合并身份；同批用户交互之后的执行沿既有重规划规则处理。

## 上下文、加载和预算

普通运行从核心工具开始，按名称加载所需工具；旧冻结请求的 `groups` schema 仍按原版本解释。本轮附件带入对应导入能力。诊断保留专用目录，不通过普通加载扩大范围。工具可见不等于用户授权。

跨轮上下文保留同对话最近的终态轮次及宿主执行记录：用户原话、说明/回答、适用的最终回复、变化、后台与跳过信息。当前轮的原 provider output、工具结果及来源 call 是规范数据。视图引用它们，不为每一步复制整段历史 JSON。

| 限制 | 当前行为 |
|---|---|
| 单工具结果的模型视图 | 16 KiB；规范结果不因视图裁剪而丢失 |
| 单批工具结果的模型贡献 | 64 KiB，计入协议包装与转义；用户回答有专门保护 |
| 历史 / 完整请求 | 128 KiB / 512 KiB，另遵守有效模型 profile 的预算 |
| 输出上限 | Chat Completions、Responses 保持 4096；官方 Messages profile 为 16384 |
| 流保护 | 1 MiB / 8192 个事件及 120 秒总时长等现有协议边界不因扩大输出值而放宽 |

压缩以完整模型往返为单位，保持 call/result 配对：先将旧工具结果换成确定存根，再移除旧往返并附宿主执行记录，必要时裁掉更早轮次；最新往返和受保护用户输入仍受约束。模型摘要尚未实现，不能用一段模型生成的“记忆”替换审计来源。

原始参数字符串、Unicode、签名/加密思考块、协议键序、`_mio_step` 包装和 `cache_control` 都属于冻结装配语义。思考续接仅按既有同轮规则保留，不把前轮思考加入新用户轮次。

## 原件、恢复和故障窗口

| durable 状态 | 原件与恢复 |
|---|---|
| intent 未提交 | 没有派发；事务失败不留下半个步骤 |
| 确定未发送的 intent | 同版本普通恢复沿用原件；已知新装配版本可从同一冻结范围重装并追加版本链 |
| dispatch_started / 结果未知 | 保留原件和已落盘 partial，不自动重发，不按当前状态猜“没发过” |
| 完整模型成功 | 与 output entry、完成证据同事务清原件；等待工具批准时仍保留冻结来源能力 |
| 失败、截断、超时或归档失败 | 保留原件与已存输出证据；归档任何阶段失败都回滚 |

成功清理之后，entries、blobs、manifest 和指定版本装配器可以重建原请求，且必须与发送时的 hash/字节数一致。缺引用、hash 不符或未知版本报错，不返回近似请求。普通读取和重建不更新记录。

近满归档先在同一事务中转换完成状态并释放原件/partial，再写通知、规范输出与来源指针，避免净占用下降却被临时双份峰值挡住。步骤的通知延后到原件释放之后，覆盖 partial 为空且字节配额恰好用满的情况；中途失败或强杀仍只能看到完整旧状态或新状态。它没有扩大配额或撤掉 SQL 约束。

## 每轮用量

用量是服务方被实际报告的被动测量，不作费用或完整性的推断。`inputTokens` 已包含缓存输入，`cacheReadTokens` / `cacheWriteTokens` 是分项，不能再加到总输入。Messages 只有必要分量齐全才得到总输入；SSE 累计快照取有效的最后值，不逐帧相加。

规范完成 entry 保存一次用量。`mio_runs.usageSummary` 只是同事务重算的小投影；读取以请求唯一身份与规范记录重算，重放不重复累计。明确未发送的 intent 不进入覆盖分母；已派发失败、unknown 和仍在进行的请求计入。没有规范计数就是未知，不用零冒充免费；本轮不新增 partial SSE 用量写入。

唯一新公开读取是：

```http
GET /api/projects/<projectId>/agent/tasks/v2/<runId>/usage
```

严格 v1 DTO 位于 `mio-run-usage.ts`：运行身份/修订、派发数、完成/失败/未知/进行中数量、四字段各自的 `knownTotals`、逐字段覆盖率与溢出标志。显式 0 与缺失的 null 不同。只有 input/cache-read 覆盖完整、input > 0 且 read ≤ input 时才返回 cacheReadRate，否则为 null。

client 提供 `usage({projectId,runId})`，校验 DTO 和运行身份。GET 不计步、不写库、不调用模型或供应商。S0 P4 前沿 K2 项目地址映射进入现有处理函数，不增加旧地址的 usage 兼容入口。原 status、snapshot、events、控制回执仍不夹带 usage、原请求或 provider output。没有新增界面、CLI 命令或模型工具目录项。

## 项目存储计量与配额

新 v2 storage 契约以 `scope: project` 和可信 projectId 标识范围，枚举完整 18 张 Mio 表。唯一 blob 只计一次；失败/unknown 原件、partial、对话 policy 及请求回执都不能漏计。全局 policy 属于应用库，不回算项目。

`usage.bytes` 对齐内核的 `MIO_QUOTA_BYTES_SQL` 文本/JSON 字段计量；`usage.rows` 对齐执行配额行式。`retained.rows` 另外披露被执行行配额豁免的编辑回执。两者都不是 SQLite 物理文件大小。doctor 在明确项目请求上返回新清单，client 校验项目身份与计量等式；旧工作区只读诊断继续使用 v1 profile。

开发期间仍为每项目 **256 MiB / 20000 行 / 单行 2 MiB**。编辑回执可在执行配额满时继续写，当前仅有单回执 payload 64 KiB 与单行保护，没有独立累计总量上限；新 DTO 明确披露 null，而非声称不存在的总量保护。它们的真实字节仍计入之后的执行占用。

新的限额由协调人按改后实测选择，本分支不提前改常量。至少 100 个同等 stress30 完整轮次的提案依据是：

```text
bytes >= C + 100 × max(B) + E
rows  >= C_rows + 100 × max(R) + E_rows
```

C 是冷启动共享成本，B/R 取完整轮和 H2 对照中的最大增量，E 明确列出保留的失败、unknown、活动 intent 与升级双份情景。旧异常可以累积，有限 E 不表示所有工作负载或无限失败都能装下。字节和行约束必须同时成立。

测量数据、四种量的区分、原始 artifact/source/lock/helper hash、命令、异常保留上界及候选数字见 [R1-C 存储测量](verification/mio-harness/R1-C-STORAGE.md) 和 [机器数据](verification/mio-harness/R1-C-STORAGE.json)。不在项目打开期间用 fs 打开/关闭数据库文件描述符。
