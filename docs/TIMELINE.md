# Durable multitrack timeline

Each project has one independent timeline. `project.get` includes it, and
`timeline.get {projectId}` reads it directly. On the first read of an existing
project the database adds an empty timeline with Video 1, Video 2 and Audio 1.
Existing shots, graph nodes, generated versions, simple exports and the project
revision are preserved. Shots are never automatically copied.

## Model and limits

The timeline has `id`, `projectId`, `revision`, `fps:30`, `width:720`,
`height:1280`, `tracks`, `clips`, `durationFrames`, `createdAt`, `updatedAt`.
It starts at revision 1. Its duration is the maximum clip end frame, or zero
when there are no clips. Maximums are 12 tracks, 100 clips and 18000 output
frames (10 minutes).

A track has `id`, `name`, `kind` (`video` or `audio`), `orderIndex`, `hidden`
and `muted`. Higher video `orderIndex` renders above lower tracks. New tracks
append at the next index. Hiding a video track suppresses only its picture;
muting suppresses all its sound, including embedded video audio. Audio tracks
cannot be hidden; they can be muted.

A clip has `id`, `trackId`, immutable `assetId`, `name`, `startFrame`,
`durationFrames`, `sourceInFrame`, `rect:{x,y,width,height}` and `gain`.
All timing values are integer frames at 30fps. Output clips start at or after
zero and last at least one frame. Convert UI seconds with `round(seconds*30)`.
Source bounds use `floor(asset.duration*30 + 0.000001)`, so a partial final
source frame is not read beyond its duration. Moving a clip changes its output
start while preserving its source in-point and duration.

- Video tracks accept PNG, JPEG, WebP, MP4 and WebM assets.
- Audio tracks accept WAV (`audio/wav`), MP3 (`audio/mpeg`) and M4A (`audio/mp4`).
- Image clips always have a source in-point of zero; their duration is chosen by the user.
- Other clips must fit fully within their source media.
- Rectangles default to the full output and must remain inside it. Coordinates
  are nonnegative even integers; dimensions are even integers of at least two
  pixels and at most 720×1280. Media fits inside the rectangle without stretching,
  with transparent padding around its original aspect ratio.
- Gain is from 0 to 2, default 1.
- Same-track clips cannot intersect. Touching edges and overlap on different
  tracks are allowed. Hidden or muted clips still occupy their timeline range.
- Gaps render as black with silence, unless another active track supplies
  picture or sound. Audio from every unmuted track is mixed, including unmuted
  video audio. There are no transitions, speed changes or time stretching.

## Operations

Every mutation requires `projectId`, `expectedRevision` (the timeline revision)
and a stable `requestId` of 8–200 characters. It returns the entire updated
timeline. Track and clip IDs are generated by the server.

- `timeline.track.add`: `kind`, optional `name`
- `timeline.track.update`: `trackId`, nonempty `patch` with `name`, `hidden` or `muted`
- `timeline.clip.add`: `trackId`, `assetId`, `startFrame`, `durationFrames`;
  optional `name`, `sourceInFrame` (0), `rect` (full output), `gain` (1)
- `timeline.clip.update`: `clipId`, nonempty `patch` with `trackId`, `name`,
  `startFrame`, `durationFrames`, `sourceInFrame`, `rect` or `gain`. Replacing the
  source asset is intentionally unsupported; remove and add a clip instead.
- `timeline.clip.remove`: `clipId`
- `timeline.undo` / `timeline.redo`: no additional fields. Traverse one saved edit;
  retain the original track/clip IDs and increment the current revision.
- `timeline.seed`: no additional fields. Only succeeds when no clips exist and
  all shots have selected versions. Copies them in shot order to the first
  video track, freezing their asset references. Later shot selection/reordering
  never modifies these clips. Missing selections or an empty shot list reject.

Each successful mutation atomically increments the timeline revision once.
Project and shot revisions are independent. Validation failures change nothing.
Stale requests return `REVISION_CONFLICT` (409) with the current timeline.
All nested input objects are strict; unknown fields are rejected.

All timeline writes and render requests share a durable request-ID namespace.
An identical retry returns the exact original response, even after later edits,
worker completion or process restart. Changing the operation or any parsed
input while reusing its request ID yields `IDEMPOTENCY_CONFLICT` (409), checked
before revision validation. A failed request does not reserve the request ID.
Never overwrite local newer state with an old replay response: fetch
`timeline.get` when reconciling an uncertain or stale operation.

## Durable edit history

`timeline.history.get {projectId}` reads metadata without creating a timeline or
writing any record. It returns `projectId`, nullable `timelineId` and `revision`,
`cursor` (number of currently applied edits), `length` (applied plus redo edits),
`canUndo`, `canRedo`, and nullable `undoEntry` / `redoEntry`. Each entry contains
its stable `id`, `operation` and `createdAt`. `project.get.timelineHistory` exposes
the same metadata alongside the current timeline.

The six edit operations (`track.add`, `track.update`, `clip.add`, `clip.update`,
`clip.remove`, `seed`) save before/after snapshots of only `tracks`, `clips` and
`durationFrames`. Undo and redo restore exactly that editing domain. They do not
roll back timeline revisions, project/shot state, selected versions, imported
media, provider jobs, provider spending or preview/export records. A seed redo
uses the original selected assets, even if shot selections changed meanwhile.
All IDs are preserved; revision numbers always move forward, including undo/redo.
An existing rendered preview consequently becomes an older snapshot after travel.

A successful new edit after undo discards the redo branch atomically. A rejected
edit preserves that branch. Old successful request responses remain replayable
exactly, including undo/redo requests whose original branch no longer exists.
Replaying them does not traverse history again. Reusing their request ID with a
changed revision or a different operation is an idempotency conflict.

`NOTHING_TO_UNDO` and `NOTHING_TO_REDO` return 409 when there is no available
entry. Existing timelines still validate `expectedRevision` first; a stale
request returns `REVISION_CONFLICT` without changing cursor or records. An undo
on a project without a timeline fails without implicitly creating one.

The timeline toolbar offers Undo/Redo with applied/total counts and next-edit
labels. Cmd/Ctrl+Z undoes, Cmd/Ctrl+Shift+Z redoes, and Ctrl+Y redoes. Shortcuts do
not capture text-entry, composition, dialog/menu interaction, or unsaved clip
edits. Pending requests disable further timeline traversal; uncertain responses
retain the exact durable request for recovery. Conflicts refresh both the timeline
and its history. Controls require a coherent, current history snapshot.

HTTP, CLI and MCP all call the same service and derive their schemas from the
shared contracts. For example, after reading the current revision:

```sh
pnpm cli timeline history get --input '{"projectId":"PROJECT_UUID"}'
pnpm cli timeline undo --input '{"projectId":"PROJECT_UUID","expectedRevision":7,"requestId":"undo-once-0001"}'
pnpm cli timeline redo --input '{"projectId":"PROJECT_UUID","expectedRevision":8,"requestId":"redo-once-0001"}'
```

MCP tools are `timeline_history_get`, `timeline_undo` and `timeline_redo`. History
reads are advertised read-only; undo/redo require caller-owned stable request IDs.

## Rendering and immutable snapshots

`timeline.render` takes `projectId`, `expectedRevision`, `requestId` and
`purpose:'preview'|'export'`. Empty timelines reject. Rendering itself does not
change the timeline revision. Preview and export use the same composition
semantics and both produce actual seekable H.264 MP4 at 720×1280, 30fps with
stereo 48kHz AAC audio.

The operation queues an ordinary export record with `mode:'timeline'`,
`purpose`, `timelineRevision`, `snapshot:{timeline,assets}`, `status`, `assetId`,
`url`, `error`, and timestamps. Each frozen asset entry includes `id`, `sha256`,
`mimeType`, `duration`, `width`, `height`, and `hasAudio` (null means unknown for
legacy assets). Managed relative paths are stored only internally and stripped
from HTTP/MCP responses.

The entire timeline and the unique referenced assets are snapshotted within
the same transaction as job creation. Database triggers prevent subsequent
changes to a timeline render's snapshot, revision and purpose. Editing the
current timeline cannot change an in-progress or completed render. Distinct
render requests create separate jobs and never overwrite an earlier output.
The worker verifies managed source paths and actual bytes against the frozen
hashes before rendering. Queued/running jobs use the existing export restart
recovery path.

Poll `export.get {exportId}` for current state. Replaying `timeline.render`
returns its original queued response, rather than the current worker state.
The result is stale when its `timelineRevision` differs from the current
timeline revision; compare revisions when displaying a preview or download.

`export.create` remains the original selected-shot-version sequence export.
It does not read or modify the multitrack timeline.

## Persistence

The additive SQLite schema contains a `timelines` table (one per project)
and an immutable `timeline_requests` table for exact saved responses. Schema v3
adds immutable `timeline_history` entries and a persisted per-project
`timeline_history_cursors` row. Existing v1/v2 tables, timeline bytes and saved
responses stay intact. Legacy timelines have no manufactured history; their first
new edit captures the existing timeline as its undo baseline. Timeline mutations and request-response writes
use `BEGIN IMMEDIATE` transactions with WAL, foreign keys and full synchronous
writes. The server's existing single-writer lock still applies.

## Asset import and UI interchange

Audio is imported through the same `asset.import` byte API and 30MiB limit as
images/video, with matching signatures and decodable stream validation.
Audio assets may also back `node.create {type:'audio',...}` canvas nodes.
Drag-and-drop uses MIME `application/x-workbench-asset` with the asset ID as
payload. A drop's horizontal position maps to a 30fps frame. Clip moves and
inspector edits go through the same revision-checked service operations as MCP.

## Optional maximum-bound check

`node scripts/stress-timeline.mjs` generates an original test image and renders
100 six-second clips to a 10-minute output in a fresh evidence directory. This
is intentionally separate from the normal test suite. The verified cloud run
produced exactly 18000 frames/600.000 seconds at 720×1280 in 234 seconds; performance
will depend on the user's computer. A separate 12-active-layer render also passed.
See `evidence/v2-tests/stress/` for the original run's metrics and probes.
