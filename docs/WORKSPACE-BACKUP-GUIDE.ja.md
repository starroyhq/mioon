# ワークスペースのオフラインバックアップ手順

この機能は現在のプロジェクトだけでなく、ワークスペース全体を扱います。SQLite には、すべてのプロジェクト、チャット、プロンプト、タスク、受領記録、履歴、データベース内の波形キャッシュがそのまま保存されます。これらは非公開の平文データです。アプリの認証情報、接続トークン、設定ファイルはコピーされませんが、プロンプトやチャットに自分で入力した機密情報はデータベースとともに保存されます。

オフラインでの作成、検証、および以下の「新しい独立したワークスペースへの安全な復元」に対応しています。復元に使えるのは対応する元のバックアップのみで、既存のワークスペースは上書きできません。復元ブランチでは新たなローカルの読み込み、編集、プレビュー、書き出しが可能です。引き継いだタスクや承認は履歴として保持され、再実行されません。現在、復元ブランチから再びバックアップを作ることはできないため、元のバックアップを必ず保持してください。すべての処理はローカルで行われ、プロバイダーへの呼び出しやタスクの自動再送信はありません。

## 操作手順

1. 右側のプロパティパネルで「ワークスペースのバックアップ」を開き、必要に応じてデータベース内の件数を読み込みます。この読み込みではメディアファイルを検査しません。また、コールドバックアップの準備完了を意味するものでもありません。
2. Mioon と、同じワークスペースを使用する Web/CLI バックエンドを通常の手順で終了します。検査を強制的に通すためにロック、WAL、journal を削除しないでください。
3. プロジェクトのロックファイルで固定された依存関係と Node24+ があるソースディレクトリで実行します。

   `node apps/cli/src/backup.mjs create --source /absolute/workspace --destination /absolute/new-backup`

   source は既存の Mioon ワークスペースです。destination は完全に新しい非公開ディレクトリで、ソースと互いを内包してはいけません。ユーザーの素材フォルダーをワークスペースとして指定しないでください。パスはローカルでのみ使用され、バックエンドやモデルに送信されません。
4. 検証します：`node apps/cli/src/backup.mjs verify --directory /absolute/new-backup`。
5. コマンドが成功し、完了マーカーとすべてのファイルの再検証が一致した場合にのみ、検証済みバックアップと呼べます。それでも、復元済みであることや、過去の有料タスクを再実行してよいことを意味しません。

desktop の既定のワークスペースの場所とリリースチャネルの違いは [DESKTOP.md](DESKTOP.md) を参照してください。カスタムの起動ディレクトリは元の起動設定に従います。このツールはディレクトリを推測したり切り替えたりしません。

## 対象範囲と上限

- 固定バージョンのディレクトリ：manifest.json、最後に公開される COMPLETE.json、および payload 内の元の SQLite、登録済みメディア、既知のタスクの一時保存済み／未確定の結果。
- データベースは最大 512MiB、1 ファイルは 8GiB、payload 合計は 64GiB、ファイル数は最大 20,000、manifest は 8MiB、ストリーミングの各ブロックは 1MiB、表示する問題は最大 100 件です。上限は空きディスク容量の保証ではありません。
- アプリの credential/settings、接続トークン、ブラウザープロファイル、独立したキャッシュディレクトリ、帰属を確認できない未知のファイルはコピーしません。データベース内の既存のキャッシュ行は保持します。
- メディアの欠落、部分的な結果、未知のタスク、除外項目は明示的に記録します。バックアップファイルの完全性を検証できても、元のプロジェクトに問題がなかったことにはなりません。
- 既存の Windows ストレージ安全チェックは、まだネイティブ環境での受け入れ検証に合格していません。初期実装は、既存の対応済み POSIX 非公開ディレクトリ方針で動作し、既存の権限を変更しません。

## ファイルの完全性とキャンセル

作成時は、終了済みの SQLite をそのままコピーします。SQL の検査は新規作成した非公開の一時コピーに対してのみ行い、ソースデータベースを開いたり移行したりしません。検証でもバックアップの親ディレクトリ内の非公開の一時コピーを使用するため、現在のユーザーが親ディレクトリに書き込める必要があります。ソースや完成済みの payload を SQL で開くことはありません。一時的な追加領域は、最大 512MiB のデータベースコピーと、最大 3 個の 64MiB SQLite sidecar です。これは 64GiB の payload 上限には含まれません。

同じワークスペースの取得を行えるのは、排他ロックを保持しているプロセスのみです。既存のロックや空でない WAL/journal があれば停止します。古いロックを削除してよいか、ツールが自動で判断することはありません。既存のディレクトリの権限は修復せず、自身の新しいディレクトリとファイルのみを 0700/0600 で作成します。この保護は他のシステムアカウントに対するもので、同じユーザーや root として動作する悪意あるプロセスを隔離するものではありません。また、ハードウェアやファイルシステムでデータが絶対に失われないことを保証するものでもありません。

Ctrl+C/SIGTERM は、その後のローカル処理の停止を要求し、すでに発行されたファイル操作の終了を待ちます。カーネル I/O を即時に中断する厳密な制限時間ではありません。中断や失敗により、完了マーカーのない新しいディレクトリが残る場合があります。保持して確認し、上書きや自動再試行はしないでください。返された公開状態が未確認の場合は、そのディレクトリを保持し、verify を別途実行してください。COMPLETE.json があるだけではバックアップの完全性を証明できません。

成功結果に SOURCE_LOCK_RELEASE_UNCONFIRMED が付いている場合、バックアップ自体は検証済みですが、ツールが自身のソースロックの解放を確認できていません。バックアップとソースロックを保持し、まず元のプロセスが終了したことを確認してください。ロックを削除して自動で再試行しないでください。失敗結果に sourceLockRelease: unconfirmed が付いている場合も、後処理が完了したとは見なせません。

## 新しい独立したワークスペースへの安全な復元

元の format1/schema24 バックアップは、独立したオフライン復元コマンドで復元できます。

```sh
node apps/cli/src/backup.mjs restore --directory /绝对路径/原始备份 --destination /绝对路径/新工作区
```

新しい復元先の親ディレクトリは存在し、復元先自体は存在しない必要があります。元のワークスペース内を選ばないでください。
ツールが検査するのは固定の祖先マーカーのみです。format1 は元のパスを保存していないため、名前が変わったすべてのソースを識別することはできません。
失敗や中断の後も復元先を保持し、ロックの削除、上書き、自動再試行はしないでください。
stdout 全体が失われた場合は、読み取り専用で確認できます。

```sh
node apps/cli/src/backup.mjs restore-status --directory /绝对路径/原始备份 --destination /绝对路径/新工作区
```

observed_guarded が示すのは、現在の復元先の固定 schema とソースの対応付けが元のバックアップと一致することだけです。前回のコマンドの成功や過去の fsync の完了を証明するものではなく、公開の補完、修復、タスクの実行も行いません。
復元ブランチを開くと、新たなローカルの読み込み、編集、プレビュー、書き出しを開始できます。引き継いだタスク、承認、結果不明の記録は履歴の状態を保持し、実行を停止します。新しい生成、Agent、Comfy、フレーム抽出、波形デコードは現在利用できません。
復元ブランチの初期実装では再びバックアップを作成することもできないため、元のバックアップの保持が必須です。
Desktop では新しいルートディレクトリの workspace サブディレクトリに復元先を置き、その新しいルートを明示的に選択してください。古い token やセッションファイルをコピーしないでください。対象範囲、制限、検証状況の詳細は[安全な復元の説明](WORKSPACE-RESTORE.md)を参照してください。
